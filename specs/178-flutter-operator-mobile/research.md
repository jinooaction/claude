# 조사 결정: 읽기 전용 Flutter 운영자 앱

## 결정 1 — 거래 엔진과 앱을 분리한다

- **결정**: auto-invest 저장소는 구조화 상태 계약만 추가하고 Flutter 코드는 별도 비공개 저장소에 둔다.
- **근거**: 휴대폰 운영체제는 장시간 worker 실행에 적합하지 않으며 앱 배포 실패가 거래 엔진을
  멈추게 해서는 안 된다. 저장소 분리는 모바일 의존성과 서명 수명주기도 격리한다.
- **검토한 대안**: Python 저장소 안에 Flutter 하위 폴더를 두는 단일 저장소는 계약 변경을 함께
  볼 수 있지만 전체 시험·배포 범위를 불필요하게 결합하므로 선택하지 않았다.

## 결정 2 — 기존 공개 상태판과 동일한 정적 JSON을 소비한다

- **결정**: 새 서버를 만들지 않고 기존 GitHub Pages 실행에서 HTML과 `status.json`을 함께 발행한다.
- **근거**: 현재 상태판은 이미 공개된 정제 sidecar만 사용하고 브로커·서버·비밀값·거래 DB에
  접근하지 않는다. 같은 입력을 재사용하면 새 돈 경로가 생기지 않는다.
- **검토한 대안**: 앱이 GitHub API 토큰이나 서버 SSH를 보유하는 방식은 휴대폰 분실 시 권한
  유출 위험이 크다. 별도 인증 API는 실제 잔고·보유종목을 추가하는 후속 명세에서 다룬다.

## 결정 3 — 첫 버전은 운영 상태만 보여준다

- **결정**: 전체 판정, 다음 행동, 돈 경로 요약, 자동화 생존 상태와 신선도만 제공한다.
- **근거**: 공개 상태판에는 실제 계좌 총액·보유종목·손익이 없다. 없는 값을 예제 숫자로 채우면
  운영자가 실제값으로 오해할 수 있다.
- **검토한 대안**: 이미지 시안의 총자산 카드는 시각 비율 참고로만 보존하고 실제 화면에서는
  전체 운영 상태 카드로 대체한다.

## 결정 4 — 알 수 없거나 오래된 값은 실패 폐쇄한다

- **결정**: 생성 후 30시간을 넘거나 시각이 미래·손상 상태이면 신선한 정상으로 표시하지 않는다.
  마지막 성공 자료를 보여줄 때는 오프라인과 생성 시각을 함께 고정 표시한다.
- **근거**: 금융 관제에서 오래된 초록색 정상은 빈 화면보다 위험하다. 30시간은 현재 일일 Pages
  발행 주기와 짧은 지연을 허용하면서 하루 이상 멈춘 상태를 드러낸다.
- **검토한 대안**: 매번 빈 화면으로 실패하는 방식은 이전 근거까지 숨긴다. 무기한 캐시는
  현재값 오인을 만든다.

## 결정 5 — 단순한 저장소와 주입 가능한 네트워크 계층을 쓴다

- **결정**: Riverpod 상태 제어기 아래에 네트워크 저장소와 기기 캐시를 두고, HTTP 클라이언트와
  캐시를 시험에서 대체할 수 있게 한다.
- **근거**: 정상·오프라인·손상 상태를 실제 네트워크 없이 결정적으로 시험할 수 있다.
- **검토한 대안**: 화면에서 직접 HTTP와 저장을 수행하면 오류 처리와 시험이 화면마다 중복된다.

## 결정 6 — Friendly Clay Finance 시각 체계를 쓴다

- **결정**: `#FFF9F5` 배경, `#30394B` 윤곽·본문, `#FDBCB4` 산호색,
  `#ADD8E6` 하늘색, `#22C55E` 정상 강조와 흰 카드, 20px 모서리, 2px 윤곽,
  5px 오른쪽 아래 그림자를 사용한다.
- **근거**: 운영자가 선택한 `Claymorphism + Vibrant & Block-based` 정체성을 유지하면서
  금융 숫자와 상태의 대비를 확보한다.
- **검토한 대안**: 유리 질감과 그라데이션은 선택한 스타일과 다르고 작은 금융 문구의 대비를 낮춘다.

## 결정 7 — 시스템 글꼴과 벡터 아이콘을 우선한다

- **결정**: 별도 원격 글꼴 없이 플랫폼 시스템 글꼴, 굵은 제목, 표 너비 숫자 기능과
  Flutter 벡터 아이콘을 사용한다.
- **근거**: 한국어 글리프 누락과 첫 실행 네트워크 의존을 없애고 금액·시각 열 정렬을 안정화한다.
- **검토한 대안**: 웹 데모의 둥근 영문 글꼴은 한국어 대체 글꼴에서 모양이 달라지고 앱 용량과
  라이선스 검토가 추가된다.

## 결정 8 — 제어 기능은 후속 안전 명세로 분리한다

- **결정**: 긴급 중단을 포함한 모든 쓰기 기능을 첫 버전에서 제외한다.
- **근거**: 긴급 중단은 안전한 하향 동작이지만 인증, 재전송 방지, 추가 전용 감사, 실제 적용 확인이
  필요하다. 중단 해제는 더 위험하므로 모바일 1차 범위에 포함할 수 없다.
- **검토한 대안**: 기존 CLI를 원격 호출하는 방식은 휴대폰에 서버 권한을 부여하므로 거부한다.
