# Feature Specification: 고정 실행 환경의 증거 계약

**Feature Branch**: `codex/215-runtime-closure-contract`  
**Created**: 2026-10-15  
**Status**: 설계 문서 검증 중 — 실행 기능 구현·설치·활성화 없음  
**Input**: 실제 예약 반영을 확인하고 고정 실행 환경의 전 범위·기동·배포 독립성·원래 코드/의존성/설치 입력 연결을 별도 명세로 구체화한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 환경 일치와 실행 자격을 구분한다 (Priority: P1)
운영자는 폴더 비교가 통과해도 어떤 실행 기반이 아직 검증되지 않았는지 알 수 있어야 한다.
**Independent Test**: 계약의 각 증거 범주와 실패 사유를 읽어 누락된 근거를 하나씩 식별한다.
**Acceptance Scenarios**:
1. **Given** 설치 폴더만 일치, **When** 전체 환경을 평가, **Then** 외부 실행 기반·기동·변경 방지의 부재를 미평가로 남기고 실행 허가를 부여하지 않는다.
2. **Given** 같은 설치 내용에 다른 시작 설정, **When** 비교, **Then** 같은 환경이라는 결론을 거절한다.

### User Story 2 - main 배포와 후보 코드 수명을 분리한다 (Priority: P1)
운영자는 일반 배포가 계속되면서도 등록에 사용한 정확 후보 코드가 바뀌지 않는 조건을 확인한다.
**Independent Test**: 배포·등록 경로 도표와 반례에서 현재 검증을 유지하는 방법을 확인한다.
**Acceptance Scenarios**:
1. **Given** main의 새 커밋, **When** 일반 배포, **Then** 후보의 정확 코드·환경·등록·관찰 시작은 자동 변경되지 않아야 한다.
2. **Given** 파일 내용은 같으나 커밋이 다름, **When** 기존 등록 검증, **Then** 불일치 거절을 유지한다.

### User Story 3 - 실제 반영과 설계 진행을 구분한다 (Priority: P2)
다음 세션은 214의 실제 반영을 재현하면서 215 문서를 새 실행 환경 출시로 오인하지 않는다.
**Independent Test**: 원래 진단·감사·고정 보관 자료와 문서의 주장 범위를 대조한다.
**Acceptance Scenarios**:
1. **Given** 원래 진단의 수집 증명 부재, **When** 인계, **Then** 시각·서명을 만들어 넣지 않고 부재를 보존한다.
2. **Given** 이 설계의 병합, **When** 완료 보고, **Then** 설계 계약 완료와 실제 설치·등록·전략 합격을 분리한다.

### Edge Cases
기반 실행파일 교체, 외부 라이브러리 변경, 기동 시 검색 경로 주입, 같은 장치의 공유 마운트,
검증 직후 교체, main 동시 배포, 동일 파일·다른 커밋, 등록의 소급 변환, 자료 지문만 있는 미인증 입력,
원래 기록 부재·가림값·과거 관측 나이, 실제 서버의 실행 기반이 아직 조사되지 않은 경우를 다룬다.

## Requirements *(mandatory)*

### Functional Requirements
- **FR-001**: 계약은 소스·의존성 입력, 설치 내용, 기반 실행파일·라이브러리, 기동·검색 경로, 플랫폼·마운트, 실행 중 불변 유지의 여섯 증거 범주를 별도로 정의한다.
- **FR-002**: 원래 입력과 실제 관측을 분리하고, 검증 대상이 즉석에서 만든 목록을 스스로 신뢰 근거로 쓰지 않는다.
- **FR-003**: 부재·불일치·변경·시간 연결 부재는 다른 사유로 남기며 어느 경우에도 실행 자격을 만들지 않는다.
- **FR-004**: 기존 정확 코드·등록 인증·연구 재계산·90초·같은 후보 60세션 검증은 보존한다. 자동 재등록·재서명·관찰 시작 초기화·문서 커밋 예외를 추가하지 않는다.
- **FR-005**: 일반 배포와 후보의 읽기 전용 코드·환경을 독립시킬 조건, 공유 허용 범위, 폐기·변경 시 거절을 문서화한다.
- **FR-006**: 다음 구현은 비밀 없는 독립 합성 검증부터 시작하고 실제 후보 설치·기동·등록·수집 인증은 통과 전략과 선행 근거가 확인될 때만 별도로 검토한다.
- **FR-007**: 설계는 213·214의 지역 비교와 전체 실행 환경 검증을 구분한다. 기존 수집기·등록 검증·시간 기록기를 복제하지 않는다.
- **FR-008**: 214의 실제 예약 반영·원래 정기 진단·부재·모의 계정 범위를 원래 자료로 재현하고 기존 고정 자료를 덮어쓰지 않는다.
- **FR-009**: 이번 산출물은 문서 계약이며 실행 코드·배포 유닛·권한·키·장부·후보·돈 경로를 변경하지 않는다.

### Key Entities
- **입력 봉인**: 검토한 정확 소스, 의존성 입력, 원래 설치 자료와 독립 신뢰 근거의 연결.
- **환경 증거**: 여섯 범주의 원래 관측과 적용 대상·시각·검증 범위.
- **기동 연결**: 비교한 환경과 실제 기동된 환경이 같다는 별도 근거.
- **실제 반영 영수증**: 같은 목표 코드의 원래 감사 행과 안전 진단 원본.

## Success Criteria *(mandatory)*
### Measurable Outcomes
- **SC-001**: 여섯 증거 범주 모두에 원래 입력·누락 판정·확인 방법이 있다.
- **SC-002**: 계약의 열두 반례 모두에 거절 또는 미평가 결과와 후속 검증 단계가 있다.
- **SC-003**: 214 원래 기록의 지문·시각·범위 대조를 보관 자료만으로 재현한다.
- **SC-004**: 이번 변경의 실행 코드·워크플로·의존성·헌법·커널 차이가 0이고 설치·실주문·새 자금 배정도 0이다.
- **SC-005**: 후속 구현 순서와 착수 조건을 읽고 설계 완료를 전략·환경·프로그램 전체 완료로 확대하지 않는다.
