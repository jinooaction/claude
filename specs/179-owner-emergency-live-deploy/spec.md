# Feature Specification: 등록 오너 단회 장중 긴급 배포

**Feature Branch**: `codex/179-operator-emergency-live-deploy`  
**Created**: 2026-09-03  
**Status**: In Progress  
**Input**: User description: "헌법을 고치고, 시스템 오너의 명시 승인으로 지금 즉시 안전하게 배포해 정상 자동 실거래까지 진행한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 특정 커밋을 지금 안전하게 배포 (Priority: P1)

저장소 오너 또는 헌법에 정확한 GitHub 계정으로 등록된 시스템 오너는 정규장 중 생산 장애를 고쳐야 할 때, 현재 `main`의 특정 커밋 하나와 이유를 명시해 한 번만 쓸 수 있는 긴급 배포를 요청한다. 시스템은 이 요청이 등록 오너 본인의 최신 요청인지 기계적으로 확인하고, 다른 협업자·커밋·나중 실행에 재사용하지 않는다.

**Why this priority**: 현재 자동 실거래 가동성 장애를 장 마감까지 방치하지 않고 고치려면 필요하지만, 영구적인 장중 배포 우회 통로가 생겨서는 안 된다.

**Independent Test**: 열린 정규장에서 유효한 오너 요청과 정확한 `main` 커밋을 제시하면 배포가 진행되고, 만료·재사용·다른 커밋·오너가 아닌 요청은 코드 변경 전에 모두 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정규장이 열려 있고 현재 `main`의 정확한 커밋과 15분 이내 만료되는 오너의 단회 요청이 있으며 모든 생산 관문이 통과한 상태, **When** 긴급 배포를 실행하면, **Then** 해당 커밋 하나만 감사 기록과 함께 배포된다.
2. **Given** 요청이 없거나 만료·재사용·등록 오너 불일치·커밋 불일치·변조 가능 상태인 경우, **When** 장중 배포가 시도되면, **Then** 생산 코드 변경 전에 실패 폐쇄되고 일반 장외 배포 경로는 그대로 남는다.
3. **Given** `push` 또는 일반 수동 배포 요청, **When** 정규장이 열려 있으면, **Then** 기존처럼 배포가 거부된다.

### User Story 2 - 배포 동안 주문을 완전히 멈추고 안전하게 복구 (Priority: P1)

운영자는 긴급 배포가 진행되는 동안 두 자동 예약 경로와 최종 중개사 쓰기가 모두 멈추고, 미체결 주문이 0건임을 확인한 뒤에만 생산 코드가 바뀌기를 원한다. 실패하면 이전 버전으로 복구하거나 주문 정지 상태를 유지해야 한다.

**Why this priority**: 장중 코드 교체보다 더 큰 위험은 교체 도중 이전 코드와 새 코드가 동시에 주문하거나, 실패 뒤 주문 권한이 열린 채 불완전한 상태가 남는 것이다.

**Independent Test**: 유지보수 잠금이 존재할 때 GitHub 예약, 서버 예약, 최종 주문 쓰기가 모두 거부되고, 성공 또는 확인된 롤백 전에는 잠금이 풀리지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 긴급 배포가 승인된 상태, **When** 생산 변경이 시작되면, **Then** 루트 소유 유지보수 잠금이 먼저 설정되고 읽기 전용 계좌 검사에서 미체결 주문 0건이 확인된다.
2. **Given** 유지보수 잠금이 설정된 상태, **When** 어느 자동 예약 경로가 주문을 시도하면, **Then** 거래일 선점을 소비하거나 중개사 쓰기를 하지 않고 실패 폐쇄한다.
3. **Given** 배포 후 건강 검사가 실패한 상태, **When** 이전 버전 복구도 확인되지 않으면, **Then** 주문 잠금과 명확한 장애 이유가 유지된다.
4. **Given** 새 버전의 90초 이상 건강 검사가 성공하거나 이전 버전 복구가 확인된 상태, **When** 긴급 실행이 종료되면, **Then** 단회 요청은 폐기되고 주문 잠금만 안전하게 해제된다.

### User Story 3 - 한 번의 승인으로 재현 가능한 운영 증거 확보 (Priority: P2)

운영자는 복잡한 서버 명령을 직접 입력하지 않고, 승인 이유와 대상 커밋을 한 번 제공해 배포 결과를 확인한다. 다음 세션은 같은 감사 기록을 보고 누가 무엇을 언제 배포했고 왜 주문이 멈췄거나 재개됐는지 재현할 수 있다.

**Why this priority**: 긴급함이 수동 명령과 기록 누락으로 이어지면 같은 문제를 다시 조사하게 된다.

**Independent Test**: 성공·거부·실패·롤백 각각에서 한 실행 식별자로 승인, 시작, 종료 상태를 따라갈 수 있고 비밀값이 노출되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 긴급 요청, **When** 배포가 시작되면, **Then** 승인 이벤트가 일반 배포 시작 이벤트보다 먼저 추가 전용 장부에 기록된다.
2. **Given** 성공 또는 실패한 긴급 배포, **When** 운영 상태를 조회하면, **Then** 대상 커밋·오너·실행 ID·이유 요약·만료·건강 검사·복구·주문 잠금 상태를 비밀값 없이 확인할 수 있다.
3. **Given** 긴급 배포가 성공한 상태, **When** 다음 정상 자동 거래가 실행되면, **Then** 기존 자본·전략·허용목록·지정가·거래일 1회·감사·대사 관문을 그대로 통과해야 주문할 수 있다.

### Edge Cases

- 승인 직후 `main`이 바뀌면 대상 불일치로 거부한다.
- 요청 유효시간 중 시계가 뒤틀리거나 발급 시각이 미래이면 거부한다.
- 같은 실행 ID 또는 요청 식별자가 다시 들어오면 거부한다.
- 요청 파일이 심볼릭 링크이거나 신뢰하지 않는 사용자가 쓸 수 있으면 거부한다.
- 읽기 전용 계좌 조회가 실패하거나 미체결 주문이 1건 이상이면 배포하지 않는다.
- 주문 잠금 설치와 거래 예약이 경쟁하면 최종 중개사 쓰기 직전의 잠금 재검사가 주문을 차단한다.
- 배포 도중 장이 닫혀도 동일 실행의 감사·건강 검사·복구 의무는 끝까지 유지한다.
- 새 버전이 건강하지만 감사 완료 기록을 남기지 못하면 잠금을 풀지 않는다.
- 확인된 롤백 뒤 정상 배포가 생산을 더 새 커밋으로 이동했어도, 정확한 현재 `main` 배포·Git 계보·건강한 worker·활성 timer·미체결 0건이 모두 증명되지 않으면 오래된 잠금을 풀지 않는다.
- 배포가 성공했지만 자동 거래 신호가 없거나 지정가가 체결되지 않으면 주문을 조작하거나 가격을 추격하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 정규장 중 일반 배포를 계속 거부하고, 헌법 VIII.A의 모든 조건을 만족한 단회 등록 오너 긴급 요청만 예외로 받아야 한다.
- **FR-002**: 긴급 요청은 정확한 현재 `main` 커밋, 저장소 오너 또는 헌법에 등록된 정확한 시스템 오너 actor, 신뢰된 실행 ID, 발급 시각, 15분 이내 만료 시각, 비어 있지 않은 이유의 다이제스트, 단회 식별자를 포함해야 한다.
- **FR-002A**: 현재 유일한 비저장소 등록 시스템 오너는 `masonoh-kidsnote`이며, 이 값은 보호된 기본 브랜치의 workflow 소스에 고정되어야 한다. actor는 입력·저장소 변수·secret·환경·협업자 역할·일반 권한 조회로 주입하거나 확대할 수 없고, 추가·변경에는 별도 헌법 개정과 위험 등급 4 검증이 필요하다.
- **FR-003**: 긴급 요청은 영구 환경 변수, 범용 강제 옵션, 브랜치 이름, 임의 원격 명령 또는 일반 배포 입력으로 표현할 수 없어야 한다.
- **FR-004**: 시스템은 요청의 소유권·권한·정규 파일 여부·시간·대상·단회성을 코드 변경 전에 검증하고, 하나라도 불명확하면 실패 폐쇄해야 한다.
- **FR-005**: 시스템은 승인 감사를 남긴 뒤 코드 변경 전에 루트 소유 유지보수 잠금을 만들고, GitHub 예약·서버 예약·최종 중개사 쓰기가 이 잠금을 각각 독립적으로 재검사하게 해야 한다. 새 잠금 코드를 모르는 이전 예약과 작업자도 중지하고 비활성 상태를 증명해야 한다.
- **FR-006**: 시스템은 이전 예약과 작업자가 정지된 상태에서 코드 변경 전 읽기 전용 중개사 검사를 통과하고 미체결 주문 0건을 증명해야 하며, 기존 보유 포지션을 자동 청산하거나 조정해서는 안 된다.
- **FR-007**: 긴급 배포는 기존 정확한 커밋, 깨끗한 소스, 강화 캐너리, 마이그레이션, 비밀값, 90초 이상 건강 검사, 롤백 관문을 우회해서는 안 된다.
- **FR-008**: 시스템은 생산 변경 전에 `DEPLOY_EMERGENCY_AUTHORIZED`와 `DEPLOY_STARTED`를 순서대로 추가 전용 감사 장부에 기록해야 한다.
- **FR-009**: 시스템은 성공 시 `DEPLOY_COMPLETED`, 실패 시 단계와 이유가 있는 `DEPLOY_FAILED`, 복구 시 기존 롤백 이벤트를 같은 상관관계 식별자로 남겨야 한다.
- **FR-010**: 단회 요청은 결과와 무관하게 재사용할 수 없게 제거해야 하며, 유지보수 잠금은 성공한 건강 검사 또는 확인된 이전 버전 복구 후에만 해제해야 한다.
- **FR-011**: 복구까지 실패하면 시스템은 주문 잠금을 유지하고 읽기 가능한 장애 이유를 제공해야 한다.
- **FR-012**: 긴급 배포는 주문 이벤트를 새로 허용하거나 자본, 전략, 승격 단계, 허용 종목, 주문 종류, 손실 한도, 거래일 선점, 정합 계약을 바꾸지 않아야 한다.
- **FR-013**: 긴급 배포 성공 뒤 실제 거래는 기존 두 자동 예약 출처 중 하나가 같은 거래일 1회 선점을 얻었을 때만 가능해야 한다.
- **FR-014**: 성공·거부·실패·복구 경로와 모든 변조·경쟁 조건은 자동화된 회귀 시험으로 재현되어야 한다.
- **FR-015**: 설치된 생산 배포 실행기가 긴급 요청 계약보다 오래된 최초 도입 상황에서는, 루트 helper가 정확한 승인 대상 `main` SHA의 격리 checkout에서 기존 배포 상태기계만 응용 프로그램 사용자로 실행해야 한다. 실행 대상은 고정 production 저장소·DB·설정·환경·감독자·90초 건강 검사여야 하며 임의 실행 파일·checkout·명령을 받을 수 없어야 한다.
- **FR-016**: 앞선 긴급 시도가 `DEPLOY_STARTED` 전에 실패해 `HALTED` 잠금을 남긴 경우, 다음 정확한 등록 오너 단회 요청은 루트 소유 정규 파일·닫힌 스키마·배타 잠금과 이전 요청의 유일한 `DEPLOY_EMERGENCY_AUTHORIZED`·`DEPLOY_STARTED=0`을 모두 증명할 때만 잠금을 인계할 수 있어야 한다. 시작됐거나 모호한 실패는 자동 인계해서는 안 된다.
- **FR-017**: 앞선 긴급 시도가 `DEPLOY_ROLLED_BACK`으로 끝났지만 shell 정리가 끊겨 요청과 `QUIESCED` 잠금이 남은 경우, 다음 정확한 등록 오너 요청은 두 파일의 루트 소유·권한·닫힌 스키마·동일 신원, 배타 잠금, 승인 1·시작 1·실패 1·커널 변경 0~1·롤백 1·완료 0·그 밖의 배포 사건 0, 최신 롤백, 생산 HEAD와 롤백 기준의 일치를 모두 증명해야 한다. 중개사 쓰기 잠금을 얻은 뒤에만 이전 요청을 제거할 수 있다. 배포 설정 검사는 systemd 환경 주입에 의존하지 않고 고정 production `.env`를 기존 비밀값 가림 loader로 읽어야 한다.
- **FR-018**: terminal rollback orphan 뒤 정상 배포가 생산 HEAD를 전진시킨 경우, 다음 정확한 등록 오너 요청은 기존 orphan의 모든 파일·신원·사건 불변식에 더해 생산 HEAD가 정확한 현재 `main` 대상임을 확인하고, rollback 기준에서 대상까지의 Git 계보, rollback 뒤 대상에 대한 일반 live 배포의 시작 1·완료 1·실패 0·롤백 0·커널 변경 0~1·예상 밖 배포 사건 0·최신 완료, 시작과 완료 사이 `WORKER_STARTED`, 현재 worker와 live timer 활성 상태를 증명해야 한다. 유지보수·중개사 쓰기 배타 잠금과 새 KIS 읽기 전용 smoke의 미체결 0건 아래에서 새 `DEPLOY_EMERGENCY_AUTHORIZED`와 `DEPLOY_EMERGENCY_RECOVERY_COMPLETED`를 추가한 뒤 이전 요청과 잠금만 제거해야 하며 코드·서비스·worker·주문을 변경해서는 안 된다. 정상 배포가 끝났고 stale 상태가 없으면 helper는 감사 가능한 무변경 no-op이어야 한다.
- **FR-019**: workflow의 성공·장중 연기·실패·긴급 helper 진입 판정은 현재 `auto-invest-deploy.service` 시작 표식부터 생성된 최신 실행 구간만 사용해야 한다. 과거 실행의 장중 거부 문구는 현재 실패를 성공이나 연기로 바꿀 수 없다. 현재 구간의 정확한 `emergency request target does not match current main` 거부는 유효한 등록 오너 단회 요청에서만 고정 root helper 호출을 허용하며, 실제 복구나 생산 변경은 helper 내부 FR-016~FR-018 증거가 모두 통과한 경우에만 가능하다.

### Key Entities

- **긴급 배포 요청**: 오너가 특정 `main` 커밋에 한 번만 부여한 짧은 수명의 배포 권한.
