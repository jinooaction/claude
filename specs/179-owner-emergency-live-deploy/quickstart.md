# Quickstart: 오너 단회 장중 긴급 배포 검증

## 1. 계약과 실패 시험

1. JSON 계약을 파싱하고 예시 요청이 추가 필드 없이 통과하는지 확인한다.
2. 요청 없음, 만료, 미래 발급, 15분 초과, 다른 SHA, 재사용 ID, 심볼릭 링크, root 아닌 소유자, group/world 쓰기 파일을 각각 거부한다.
3. 열린 XNYS에서 요청 없는 일반 배포가 계속 `market_hours_guard`로 막히는지 확인한다.

## 2. 주문 정지 경쟁 시험

1. 승인 감사를 남기고 유지보수 잠금 파일을 만든다.
2. 새 잠금 코드를 모르는 이전 scheduler timer·service·worker도 중지하고 비활성인지 확인한다.
3. 정지 뒤 KIS 읽기 전용 검사에서 미체결 주문 0건을 확인한다.
4. GitHub 라이브 helper와 서버 timer helper가 거래일 선점 전 거부되는지 확인한다.
5. 이미 실행 중인 주문 router가 각 KIS 쓰기 직전에 거부 감사를 남기고 제출 0건인지 확인한다.
6. 잠금이 없을 때 기존 예약·주문 회귀가 변하지 않는지 확인한다.

## 3. 배포 상태 기계 시험

1. 유효 요청에서 `DEPLOY_EMERGENCY_AUTHORIZED`가 `DEPLOY_STARTED`보다 먼저 같은 상관관계 ID로 기록되는지 확인한다.
2. 정상 건강 검사에서 성공하고 요청과 잠금이 제거되는지 확인한다.
3. 건강 실패·복구 성공에서 이전 SHA가 복구되고 잠금이 제거되는지 확인한다.
4. 복구 실패에서 요청은 제거되지만 잠금이 남고 주문이 계속 차단되는지 확인한다.

## 4. 전체 품질 관문

1. 관련 pytest와 shell syntax 검사를 통과한다.
2. `uv run pytest`와 `uv run ruff check src tests`를 통과한다.
3. strict agent harness와 HANDOFF 사실 검사를 통과한다.
4. 위험 등급 4와 K6/K-meta 변경을 담은 PR 본문 품질 관문을 통과한다.

## 5. 생산 인수 시험

1. main 머지 뒤 기존 push 배포가 새 root helper와 unit을 동기화한 다음 일반 장중 차단으로 멈추는지 확인한다.
2. namespace 소유자 또는 헌법 15.0.1에 정확히 등록된 시스템 오너가 정확한 main SHA, 확인 문구, 이유로 긴급 workflow를 한 번 실행한다.
3. KIS smoke `6/6`, `open_unfilled=0`, 승인/시작/완료 감사, exact-main 생산 HEAD, 90초 건강 검사를 확인한다.
4. 다음 GitHub schedule 또는 server timer 자동 실행에서 기존 10% 단 1 계약으로 실제 주문·체결·전략 감사·계좌 대사를 확인한다.
5. 다른 scheduler가 같은 최초 run을 반환하고 중복 중개사 쓰기가 0건인지 확인한다.

## 되돌림

- 기능 문제가 있으면 별도 PR로 이전 구현을 되돌린다.
- 생산 배포 실패는 기존 runner가 이전 SHA로 자동 복구하고 건강 상태를 확인한다.
- 복구가 확인되지 않으면 유지보수 잠금을 지우지 않고 실주문을 멈춘 채 장애 원인을 노출한다.
- 헌법 15.0.1의 예외이나 등록 오너를 되돌리거나 바꿀 때도 K-meta 전용 개정 커밋과 새 버전이 필요하다.
