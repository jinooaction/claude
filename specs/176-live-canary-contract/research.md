# 연구 결정: 증거 수렴형 실거래 검증 캐너리

## 결정 1 - 운영 검증과 확정 알파를 분리한다

**결정**: 장기 시간 분리 성과·정확 배포 지문·강화 검사·체결 대리·정수 주 구현성을 통과한
기존 전략은 10% 운영 캐너리에 들어갈 수 있다. 이 상태의 `alpha_confirmed`는 항상 거짓이다.

**근거**: `globalfixed`는 235개월 홀드아웃에서 50bp 비용 후 샤프 1.83, 최대 낙폭 5.58%로
운영 시험 후보로 충분히 안정적이다. 그러나 벤치마크 초과수익 PSR 약 0.612와 100bp 이상에서
약해지는 초과수익은 확정 알파라고 부르기 부족하다.

**기각한 대안**: 모든 실거래를 깨끗한 전진 40표본까지 금지하면 실제 주문·체결 배관은 계속
검증되지 않는다. 반대로 기존 알파 기준을 낮추면 과거 장부 오류를 성과로 인정하게 된다.

## 결정 2 - 오염된 전진 표본은 재사용하지 않는다

**결정**: 의도치 않은 차입을 포함했던 42~47개 과거 전진 관측은 포렌식 기록으로만 보존하고,
승격 표본에는 포함하지 않는다.

**근거**: 음수 현금은 레버리지 없는 전략과 다른 위험을 만들며 PSR·칼마·낙폭을 왜곡한다.

## 결정 3 - 첫 운영 자본은 최신 NAV의 최대 10%다

**결정**: 단 0에서 단 1로만 진입하며 금액은 최신 실계좌 NAV × 0.10을 센트 단위로 내림한다.
전략 지문과 정수 주 구현성이 맞지 않으면 0을 유지한다.

**근거**: 실제 주문·체결·슬리피지·정합을 작은 노출로 확인하면서 손실 예산과 포지션 한도를
보존할 수 있다.

## 결정 4 - 20% 승격 기준은 그대로 둔다

**결정**: 운영 캐너리의 기간이나 체결 수가 늘어도 그것만으로 단 2에 오르지 않는다. 깨끗한
전진 40관측, PSR 0.80, 칼마 우위, 정확 전략 지문, 강화 검사, 전체 경로 교정을 별도로 요구한다.

## 결정 5 - 증거는 원시 월별 요인과 소비자 재계산을 포함한다

**결정**: 운영 증거는 홀드아웃 월, 후보 요인, 기준 요인, 비용 모형을 보관하고 자본 판정기가
CAGR·샤프·낙폭·초과수익 PSR·비용 민감도를 다시 계산한다.

**근거**: 한 프로그램이 만든 `eligible:true`를 같은 프로그램이 그대로 신뢰하면 숫자·기간·비용
계약의 오류를 잡을 수 없다.

## 결정 6 - PEAD 진단과 자본 진입 파일을 분리한다

**결정**: `strategy_factory.json`은 최신 연구 진단으로 유지하고, 자본 소비자는 역할이
`capital_entry_evidence`인 별도 파일만 읽는다. 운영 캐너리 증거도 별도 파일로 발행한다.

**근거**: 현재 한 워크플로에서 회계 요인 결과 뒤 PEAD 결과가 같은 파일을 덮어써 역할이 섞인다.

## 결정 7 - 실제 주문은 검증된 공통 경계만 사용한다

**결정**: 임의 시장가 주문이나 수동 주문 스크립트를 만들지 않는다. 배포·sidecar·센티넬을 먼저
일치시킨 뒤 지정가·정규장·거래일 선점·위험·감사 공통 경계를 사용한다. 최초에는
`rebalance-live-canary`의 서명된 GitHub 경로만 허용했으며, 생산에서 동일 공급자 예약 실패가
확인된 뒤 결정 17이 root 소유 서버 fallback을 같은 공통 경계 안에 추가한다.

## 결정 8 - 실제 체결 전에는 목표를 완료하지 않는다

**결정**: 주문 요청만 접수됐거나 시장이 닫힌 상태를 완료로 보지 않는다. 체결 조회, 전략 장부,
계좌 정합, 추가 전용 감사 기록이 같은 실행에 연결될 때 완료로 판정한다.

## 결정 9 - 정각 UTC 예약 대신 뉴욕 현지 비정각 예약을 쓴다

**결정**: 실거래 캐너리는 `America/New_York` 10:17 평일 예약을 최초 기회로 사용한다.
마이크로 GTAA의 기존 15:00 UTC 예약은 별도 경로이므로 바꾸지 않는다. 단일 예약 누락이
생산에서 확인된 뒤의 복수 기회 보정은 결정 13이 이 결정을 확장한다.

**근거**: 최근 `rebalance-live-canary` 예약 실행은 정각 혼잡 아래 42~80분, 두 차례는 약 9시간
지연됐다. GitHub 공식 문서도 매시 정각 예약의 지연·누락 가능성과 비정각 예약을 권고한다.
뉴욕 현지 시각을 쓰면 서머타임 전환에도 정규장 초반이라는 의미가 유지된다.

**기각한 대안**: 하루 여러 번 실주문 예약을 추가하면 지연 내성은 높아지지만, 미체결 주문과
중복 재조정의 위험 표면을 넓힌다. 첫 실제 체결 전에는 단일 비정각 예약이 더 작은 변경이다.

## 결정 10 - 운영 표의 성공 문자열이 아니라 섹션 JSON을 사실로 쓴다

**결정**: money-path는 생산 라이브 sidecar의 `첫 체결 전 최신 엣지 재검증` 제목 아래 펜스
안에서 첫 JSON 객체를 읽고, `allowed`와 `state`를 마지막 preflight 상태로 표시한다. 같은
문구가 있는 요약 표 행이나 작업 결과 `success`만으로 통과를 추론하지 않는다.

**근거**: 실제 생산 로그는 JSON 앞에 증거 나이와 원격 명령 종료 코드를 한 줄로 기록한다.
기존 파서는 펜스 전체가 순수 JSON이라고 가정했고, 표 행을 제목보다 먼저 찾아 드라이런
미리보기 블록까지 잘못 소비했다. 그 결과 성공한 `ENTRY_READY`를 증거 없음으로 표시했다.

**실패 폐쇄**: 제목 범위 안에 boolean `allowed`가 있는 JSON 객체가 없으면 이전과 같이
`preflight evidence absent`를 유지한다. 사람용 표의 `success`는 보조 정보로만 남긴다.

## 결정 11 - 레거시 캐너리 자본 설정을 현재 10% 계약의 이중 검사로 쓴다

**결정**: 라이브 설정의 `canary_capital_pct`를 단 1 운영 증거의 10%와 맞추고, 첫 주문
재검사가 두 값을 직접 대조한다. 센티넬과 최신 NAV가 실제 금액의 권위이며 이 설정은 같은
의도를 독립적으로 확인하는 선언이다.

**근거**: 스펙 001에서 도입한 5% 필드는 설정 검증만 되고 실제 주문 금액 계산에는 쓰이지
않았다. 스펙 176은 헌법 X.4에 따라 첫 자본을 정확히 NAV 10%로 다시 정의했지만 생산 설정에
옛 5%가 남아, 안전 한도처럼 보이는 값과 실제 계약이 달랐다. 값을 단순히 고치는 데 그치면
다시 어긋나도 발견하지 못하므로 첫 주문 관문에서 불일치를 실패 폐쇄한다.

**기각한 대안**: 5%를 실제 주문 상한으로 뒤늦게 적용하면 확정된 10% 명세·헌법과 충돌하고
현재 정수 주 구현성 계약도 달라진다. 필드를 삭제하면 과거 설정 호환성과 명시적 이중 검사를
잃는다.

## 결정 12 - 예약 시각과 실제 주문 시각을 분리해 검증한다

**결정**: `rebalance-once`의 실주문 모드는 서버의 실제 현재 시각을 XNYS 달력으로 검사하고,
정규장 밖이면 DB 마이그레이션이나 KIS 조회 전에 종료 코드 75로 실패 폐쇄한다. 시작 때 열린
장도 `OrderRouter`가 실행 권한 잠금을 얻은 뒤 각 실제 중개사 쓰기 직전에 같은 검사를 다시
수행한다. 도중 마감은 `market_hours_gate` 감사 거부로 남기고 CLI와 워크플로까지 종료 코드
75를 전파한다. 종이매매와 주문 없는 미리보기에는 적용하지 않으며 우회 옵션을 만들지 않는다.

**근거**: 비정각 뉴욕 10:17 예약은 혼잡 가능성을 낮출 뿐 실제 시작 시각을 보장하지 않는다.
이력에는 약 9시간 지연도 있어 무장 뒤 같은 지연이 재발하면 장 마감 후 주문을 시도한다. 실제
돈을 움직이는 가장 안쪽 공통 진입점에서 주문마다 재검사해야 GitHub 지연, 긴 사전 조회, 순차
주문 및 다른 호출 경로를 함께 막는다.

**기각한 대안**: 워크플로 이벤트 시각만 검사하면 러너 대기 시간을 놓치고, KIS의 장외 거부에
맡기면 불필요한 주문 시도와 오류 장부가 생긴다. 셸 게이트만 추가하면 다른 `rebalance-once`
라이브 호출이 보호되지 않는다.

## 결정 13 - 단일 예약을 거래일 1회 선점이 있는 복수 예약으로 바꾼다

**결정**: 뉴욕 현지 10:17, 11:17, 12:17, 13:17에 예약 실행 기회를 둔다. production 서버는
서명·센티넬·배포 정합과 XNYS 정규장 검사를 통과한 첫 실행이 뉴욕 거래일 키를 파일 잠금 아래
추가 전용으로 선점하게 한다. 같은 거래일의 후속 실행은 원래 run ID를 보고하고
`rebalance-once`를 호출하지 않는다. 무장 상태의 preview job은 production sidecar를 발행하지
않고, 서버가 중복으로 판정한 run도 체결 동기화·측정·정합·sidecar 발행을 생략한다.

**근거**: 2026-08-31 10:17 뉴욕 예약은 10:32가 지나도록 GitHub run 자체가 만들어지지 않았다.
비정각 한 건도 지연·누락될 수 있으므로 단순 대기는 실제 자동매매의 생존성을 보장하지 못한다.
반대로 중복 예약만 추가하면 미체결 주문 재제출과 최신 sidecar 덮어쓰기 위험이 생긴다. 서버의
거래일 선점이 주문 경로를 정확히 한 번으로 줄이고, preview 발행 제한이 최초 실행 증거를 보존한다.

**기각한 대안**: 장중에 수동 `workflow_dispatch`를 실주문화하면 승인 경계와 재현성을 잃는다.
공통 재검증과 거래일 선점 없이 서버 타이머가 직접 `rebalance-once`를 부르면 기존 안전 경계를
우회한다. 선점 없이 복수 cron만 추가하면 중복 주문과 증거 덮어쓰기 표면이 커진다. 이때 보류한
독립 서버 경로는 이후 생산 증거를 반영한 결정 17에서 더 좁은 root 소유 형태로 다시 설계한다.

## 결정 14 - 같은 안전 경계 안에서 예약 기회를 촘촘하게 한다

**결정**: 뉴욕 현지 10:17부터 13:53까지 최대 12분 간격으로 라이브 캐너리 예약 기회를 둔다.
10시에는 17·29·41·53분, 11시부터 13시에는 05·17·29·41·53분이다. GitHub의 `schedule`
이벤트, main 전용 기계 승인, production 서명, XNYS 정규장 검사와 서버 거래일 1회 선점은 그대로
유지한다. money-path도 현재 시각 뒤 가장 가까운 이 후보를 표시한다.

**근거**: 2026-08-31에는 10:17 예약 누락 보정이 main에 들어온 뒤에도 12:17 예약 run이 목표
시각 뒤 생성되지 않았다. 시간당 한 번의 후속 기회는 누락을 감지해도 다음 복구까지 거의 한
시간을 더 기다리게 한다. 12분 간격의 비정각 후보 19개는 동일한 외부 예약 서비스 안에서도
독립적인 발화 기회를 늘리고, 이미 구현된 거래일 선점은 그중 최초 유효 실행만 주문으로 보낸다.

**기각한 대안**: `workflow_dispatch`를 실주문화하거나 `repository_dispatch`라는 새 주문 승인
이벤트를 추가하면 공격·오작동 표면이 넓어진다. 공통 진입 재검증·거래일 선점·사후 증거 없이
production 서버 타이머가 직접 주문하는 것도 금지한다. 5분 간격은 회복 기회 증가 대비 불필요한
러너·미리보기 부하가 더 크다. GitHub 내부 후보만으로 충분하다는 판단은 결정 17의 생산 증거로
폐기한다.

## 결정 15 - 배포 감사도 고정된 읽기 전용 원격 명령으로 수행한다

**결정**: `deploy-audit-log.yml`은 SSH로 임의 셸 본문을 보내지 않고 forced-command gateway의
`deploy-audit [correlation_id]`만 호출한다. gateway와 root 소유 helper가 correlation ID를 각각
8~64자리 16진수로 검사하고, helper는 고정 데이터베이스의 `DEPLOY_%` 행을 읽기 전용으로 조회한다.

**근거**: 생산 run `33439750122`는 `REQUESTED_CID='' bash -s`를 호출해 보안 경계에서 종료 코드
126으로 정상 거부됐다. 이는 배포 실패 증거가 아니라 관측기와 보안 경계의 계약 불일치다. 감사
조회 자체를 허용 목록 명령으로 만들면 기존의 임의 원격 셸 금지를 보존하면서 배포 증거를 읽을 수 있다.

**기각한 대안**: gateway가 환경 변수 접두사나 `bash -s`를 허용하게 넓히면 GitHub 키가 임의 root
명령 실행 경로를 얻게 된다. workflow에 SQL을 계속 두거나 `deploy-journal` 문자열만으로 배포 성공을
추론하면 서버 DB의 추가 전용 감사 사슬을 독립 검증하지 못한다.

## 결정 16 - 거래소 후보의 5xx는 다음 시세 후보를 읽되 최종 장애는 보존한다

**결정**: `get_quote_resolving_market`은 한 EXCD 조회가 5xx로 끝나면 다음 `NAS/NYS/AMS` 후보를
계속 읽는다. 다른 후보에서 양의 시세가 나오면 그 실제 거래소를 반환한다. 모든 후보가 실패하면
마지막 5xx를 다시 던지고, 4xx는 즉시 전파한다.

**근거**: exact-main KIS smoke run `33442299948`에서 AAPL·현금·보유·잔고·미체결은 정상인 반면,

## 결정 17 - GitHub와 독립된 root 소유 서버 fallback을 같은 일일 선점에 연결한다

**결정**: GitHub `schedule`을 주 경로로 유지하되, production 서버의 root 소유
`auto-invest-live-canary.timer`가 뉴욕 현지 10:35부터 별도 비정각 시각에 fallback을 깨운다.
fallback은 원격 주문 명령이나 새 GitHub 이벤트가 아니다. 고정 systemd unit 신원, exact-main,
10% 센티넬, 동일한 첫 진입 재검증, XNYS 정규장, 킬스위치·손실·정합·허용 종목·K1·지정가를
검사한 다음 기존 거래일 선점 장부를 `source=server_timer`로 차지한다. GitHub와 서버 중 먼저
선점한 한 실행만 `rebalance-once`에 도달한다. 선점 뒤 실패도 같은 날 재시도하지 않는다.

**근거**: 2026-08-31의 19개 GitHub 후보는 같은 예약 공급자에 묶여 있었고, 실제 schedule run은
마지막 장중 후보보다 네 시간 넘게 늦게 생성됐다. 횟수는 늘었지만 장애 영역은 하나였으므로
복원력이 생기지 않았다. production 서버의 systemd는 GitHub 예약 생성과 독립되어 있고, 이미
배포·튜닝 자동화에서 운영되는 로컬 시간원이다. 첫 GitHub 후보보다 18분 늦은 10:35부터 발화하면
정상 GitHub 실행에 우선권을 주면서도 전부 누락된 날을 같은 정규장 안에 복구한다.

**권한 경계**: GitHub 경로는 기존 짧은 수명 Ed25519 서명과 nonce를 유지한다. 서버 경로는 새
비밀키를 만들지 않고 root 소유 unit과 root 소유 helper만 신뢰한다. deploy SSH forced-command는
fallback 주문을 노출하지 않고, 고정 읽기 전용 최신 실행 상태만 조회할 수 있다. 두 경로 모두
같은 root 소유 시장 세션 파일과 `flock`을 사용하므로 권한 출처가 둘이어도 broker write 권한은
거래일당 하나다.

**사후 증거**: 서버 최초 실행은 주문 단계의 성공 여부와 무관하게 체결 동기화, 성과 측정,
계좌 정합을 시도하고 정화된 실행 요약을 추가 전용 로컬 디렉터리에 남긴다. 뒤늦은 GitHub 실행은
공유 선점의 최초 출처와 run ID를 읽고 broker call 없이 이 서버 증거를 production sidecar에
발행한다.

**기각한 대안**: 19개 GitHub cron을 더 늘리는 것은 상관된 장애를 해결하지 못한다.
`workflow_dispatch` 또는 `repository_dispatch` 실주문화는 수동·토큰 기반 원격 주문 표면을 넓힌다.
서버가 GitHub API를 호출하는 방식은 새 장기 GitHub 쓰기 토큰을 production에 두고 GitHub runner
가용성에도 계속 의존한다. 공통 선점 없이 서버가 별도 주문 CLI를 부르면 중복 주문 위험이 생긴다.

## 결정 21 - 성공 요약이 없을 때는 고정 systemd 실행 상태만 정화해 읽는다

**결정**: 기존 root 소유 live helper에 인자를 받지 않는 `runtime-status`를 추가한다. 읽는 값은

`systemd-order`, 환경 전체와 비밀값은 노출하지 않는다. 이 자료는 실패 진단일 뿐 실제 주문·체결·
감사·대사의 성공 증거를 대신하지 않는다.

**기각한 대안**: 원격 `journalctl`이나 임의 `systemctl`을 허용하면 SSH 경계가 넓어진다. 성공
요약 형식을 조기 실패까지 섞어 확장하면 최초 선점·주문·사후 대사가 완료된 증거의 의미가 흐려진다.
서버 서비스를 수동 시작해 재현하면 자동 예약 증거와 하루 1회 돈 경로를 훼손한다.

## 결정 22 - 주문 0건은 해당 실행의 정화된 결과 상태로 진단한다

**결정**: server timer 성공 요약이 `orders_submitted=0`이면, 같은 14자리 run ID 아래 root 전용
`order.log`의 마지막 유효 CLI JSON만 읽는 `scheduled-order-diagnostics`를 호출한다. 반환값은
계획/결과/보류 건수, 종목, 방향, 요청·라우팅 정수 수량, 허용된 결과 상태, 안전한 gate와 고정
보류 코드로 제한한다. 원문 reason과 가격·현금·계좌·주문 식별자는 버린다.

**근거**: 2026-09-03 자동 server timer는 exact main에서 첫 진입 재검증과 거래일 선점, 체결 동기화,
측정, 정합까지 성공했지만 요약은 주문 0건만 남겼다. 기존 요약만으로는 주문 계획이 없었는지,
위험 gate가 막았는지, 브로커가 거부했는지, 단순 집계 오류인지 구분할 수 없다. 이유를 모른 채
거래일 선점을 지우거나 재시도하면 중복 주문 위험이 생긴다.

**안전 경계**: 임의 경로·로그·원문 오류를 노출하지 않고 최신 또는 명시된 14자리 실행 디렉터리의
일반 파일만 읽는다. JSON 키·상태·수량·종목을 서버와 GitHub가 이중 검증한다. 이 경로는 읽기
전용이며 오늘의 선점, 주문 정책, 자본, 서비스 상태를 바꾸지 않는다.

**기각한 대안**: 요약의 주문 수만 보고 자동 재시도하면 브로커 접수 불명확 상태를 중복 주문으로
바꿀 수 있다. journal 원문이나 `order.log` 전체를 원격으로 내보내면 계좌·가격·브로커 오류와
비밀값 경계가 넓어진다. 다음 날까지 기다리는 것은 같은 원인을 재현할 뿐 진단이 아니다.

## 결정 23 - 브로커 거부는 원문 대신 고정 KIS 코드와 주문 분류만 공개한다

`kis_rt_cd`, `kis_msg_cd`, HTTP 상태, 예외 종류, 고정 주문 TR ID, `NASD|NYSE|AMEX` 거래소와

**근거**: 생산 자동 실행은 IAUM과 SCHX 주문을 실제 제출 경로까지 보냈지만 둘 다 명시적으로
브로커 거부됐다. 결과 상태만으로는 공통 주문 형식 문제와 종목별 거래소 문제를 나눌 수 없고,
같은 요청을 재시도할 근거도 없다. 고정 코드는 원인을 특정하는 데 충분하면서 비밀 경계를 넓히지 않는다.

**안전 경계**: 읽는 파일·run ID·상태는 기존 경계를 재사용한다. 거부 결과 수와 진단 수를 맞추고
모든 값에 닫힌 형식을 적용한다. 이 진단은 주문·재시도·서비스 제어 권한을 추가하지 않는다.

## 결정 24 - 공식 KIS 공통 헤더와 production 주문 요청을 맞춘다

**기각한 대안**: 공개 의미가 확인되지 않은 `APBK1672`를 임의의 재시도 가능 코드로 분류하거나,

재시도가 필요해지면 기존 첫 선점을 수정하지 않는 별도 헌법·돈 경로 계약으로만 설계한다.

## 결정 26 - live rebalancer의 KIS REST 호출을 burst 없이 5회/초로 직렬화한다

**결정**: 2026-09-04 자동 server timer 최초 실행 `20260904143505`는 `ENTRY_READY`와 공통
선점을 통과했지만 IAUM 첫 주문이 HTTP 500·`EGW00201`로 명시적 거부되고, 이어진 SCHX 주문도
HTTP 200·`APBK1672`로 명시적 거부되어 접수 0건으로 끝났다. KIS 공식 현재 구현은 production
REST 호출 시작 사이에 최소 0.05초를 보장하지만 우리 live rebalancer는 15-token 초기 bucket으로
계좌·시세·주문 요청을 순간 burst할 수 있었다. production live rebalancer의 제한기를
`rate_per_sec=5.0`, `capacity=1.0`으로 고정해 모든 호출을 최소 0.2초 간격으로 직렬화한다.

**근거**: `EGW00201`은 KIS 공식 저장소가 명시한 초당 거래건수 초과 코드다. 평균 15회/초인
기존 설정도 초기 15개 요청을 즉시 통과시키므로 최소 간격 계약이 아니었다. 5회/초는 공식 실전
권고보다 네 배 보수적이며 이 소액 2종목 리밸런스의 장중 완료 시간에는 실질 영향이 없다.

**안전 경계**: 주문의 `retry_transient=False`를 유지해 HTTP 응답이 불명확한 쓰기를 같은
프로세스가 재전송하지 않는다. 기존 지정가·허용 종목·NAV 10%·주문별 정규장·거래일 선점·
추가 전용 감사·대사는 유지한다. 현재 사고는 모든 결과가 명시적 거부이고 열린 주문·체결·
사후 오류가 0인 exact manifest로만 기존 별도 복구 슬롯을 한 번 쓸 수 있다.

**기각한 대안**: `EGW00201` 응답을 즉시 자동 재전송, 시장가 전환, 첫 선점 삭제, 수동 주문,
수동 service 시작은 중복·가격 위험을 넓혀 기각한다. 공개 의미를 확인하지 못한 `APBK1672`를
임의 분류하거나 거래소를 바꾸는 수정도 기각한다.

약관 신청을 대신 수행하는 안전한 API는 확인하지 못했다.

**결정**: 추가 주문 코드 변경이나 세 번째 같은 날 재시도 대신 운영자가 KIS 앱에서 본인 인증과
약관 동의를 직접 완료한다. 완료 뒤에만 다음 정상 자동 scheduler 실행으로 주문 접수·체결·전략
감사·계좌 대사와 중복 주문 0건을 검증한다.

**안전 경계**: 시스템은 금융 서비스 약관에 대신 동의하지 않고, 계좌 설정을 추측해 바꾸지 않으며,
수동 주문·수동 live service 시작·가격 추격·거래일 선점 삭제를 하지 않는다. 주제 분류는 계좌 영역을
좁히는 진단일 뿐 신청 완료 증거나 `APBK1672`의 공식 코드 정의가 아니다.

## 결정 29 - 서비스 신청 원문은 숨긴 채 확인 범위만 더 좁힌다

**문제**: 진단 1.2는 IAUM·SCHX의 공통 거부를 `account`, `service_registration`으로 좁혔지만,
운영자가 먼저 확인할 항목이 해외증권 거래신청인지 해외 ETP 거래신청인지는 구분하지 못한다.
두 신청을 무조건 모두 바꾸라고 하면 확인되지 않은 계좌 변경을 권하게 되고, root 전용 `msg1`
원문을 공개하면 비밀·계좌 정보 경계를 깨뜨린다.

**공식 근거**: 위 한국투자증권 공식 해외주식 거래안내는 해외증권 거래신청 뒤 거래가 가능하다고 안내하고,
해외 ETF·ETN은 해외증권 신청 뒤 별도 해외 ETP 거래신청이 필요하다고 구분한다. 공개 Open API
주문 안내에서도 해외주식 서비스 신청은 선행 조건이지만, 기존 개인 계좌의 신청 상태를 읽거나
약관에 동의하는 안전한 공개 API는 확인하지 못했다.

**결정**: 진단 스키마 1.3은 기존 닫힌 주제에 `service_registration_scopes`를 추가한다. 값은
`overseas_securities`, `overseas_etp`, `overseas_volatility_etn`, `generic_service`,
`not_applicable`, `unavailable`만 허용한다. 서비스 신청 주제와 범위가 모순되면 server helper와
observer가 모두 발행을 거부한다. 생산의 이미 끝난 실행을 읽기 전용 observer로 다시 분류해
운영자 확인 지점을 좁히되, 신청 상태 자체를 확인했다고 주장하지 않는다.

**안전 경계**: 원문·부분 문자열·길이·해시·계좌·가격·주문 식별자는 계속 0건이다. 이 변경은
주문·재시도·service/timer 시작·거래일 선점·금융 약관 동의 권한을 추가하지 않는다. 범위가
`generic_service`면 두 공식 신청을 운영자가 확인하고, 구체 범위가 나와도 본인 인증과 약관 동의는
운영자만 수행한다.
