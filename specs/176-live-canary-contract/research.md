# 연구 결정: 증거 수렴형 실거래 검증 캐너리

## 결정 1 - 운영 검증과 확정 알파를 분리한다

**결정**: 장기 시간 분리 성과·정확 배포 지문·강화 검사·체결 대리·정수 주 구현성을 통과한
기존 전략은 10% 운영 캐너리에 들어갈 수 있다. 이 상태의 `alpha_confirmed`는 항상 거짓이다.

**근거**: `globalfixed`는 235개월 홀드아웃에서 50bp 비용 후 샤프 1.83, 최대 낙폭 5.58%로
운영 시험 후보로 충분히 안정적이다. 그러나 벤치마크 초과수익 PSR 약 0.612와 100bp 이상에서
약해지는 초과수익은 확정 알파라고 부르기 부족하다.

**기각한 대안**: 모든 실거래를 깨끗한 전진 40표본까지 금지하면 실제 주문·체결 배관은 계속
검증되지 않는다. 반대로 기존 알파 기준을 낮추면 과거 장부 오류를 성과로 인정하게 된다.

## 결정 2 - 오염된 전진 표본은 재사용하지 않는다

**결정**: 의도치 않은 차입을 포함했던 42~47개 과거 전진 관측은 포렌식 기록으로만 보존하고,
승격 표본에는 포함하지 않는다.

**근거**: 음수 현금은 레버리지 없는 전략과 다른 위험을 만들며 PSR·칼마·낙폭을 왜곡한다.

## 결정 3 - 첫 운영 자본은 최신 NAV의 최대 10%다

**결정**: 단 0에서 단 1로만 진입하며 금액은 최신 실계좌 NAV × 0.10을 센트 단위로 내림한다.
전략 지문과 정수 주 구현성이 맞지 않으면 0을 유지한다.

**근거**: 실제 주문·체결·슬리피지·정합을 작은 노출로 확인하면서 손실 예산과 포지션 한도를
보존할 수 있다.

## 결정 4 - 20% 승격 기준은 그대로 둔다

**결정**: 운영 캐너리의 기간이나 체결 수가 늘어도 그것만으로 단 2에 오르지 않는다. 깨끗한
전진 40관측, PSR 0.80, 칼마 우위, 정확 전략 지문, 강화 검사, 전체 경로 교정을 별도로 요구한다.

## 결정 5 - 증거는 원시 월별 요인과 소비자 재계산을 포함한다

**결정**: 운영 증거는 홀드아웃 월, 후보 요인, 기준 요인, 비용 모형을 보관하고 자본 판정기가
CAGR·샤프·낙폭·초과수익 PSR·비용 민감도를 다시 계산한다.

**근거**: 한 프로그램이 만든 `eligible:true`를 같은 프로그램이 그대로 신뢰하면 숫자·기간·비용
계약의 오류를 잡을 수 없다.

## 결정 6 - PEAD 진단과 자본 진입 파일을 분리한다

**결정**: `strategy_factory.json`은 최신 연구 진단으로 유지하고, 자본 소비자는 역할이
`capital_entry_evidence`인 별도 파일만 읽는다. 운영 캐너리 증거도 별도 파일로 발행한다.

**근거**: 현재 한 워크플로에서 회계 요인 결과 뒤 PEAD 결과가 같은 파일을 덮어써 역할이 섞인다.

## 결정 7 - 실제 주문은 기존 예약 워크플로만 사용한다

**결정**: 임의 시장가 주문이나 수동 주문 스크립트를 만들지 않는다. 배포·sidecar·센티넬을 먼저
일치시킨 뒤 기존 `rebalance-live-canary`의 서명된 지정가·정규장 경로를 사용한다.

## 결정 8 - 실제 체결 전에는 목표를 완료하지 않는다

**결정**: 주문 요청만 접수됐거나 시장이 닫힌 상태를 완료로 보지 않는다. 체결 조회, 전략 장부,
계좌 정합, 추가 전용 감사 기록이 같은 실행에 연결될 때 완료로 판정한다.

## 결정 9 - 정각 UTC 예약 대신 뉴욕 현지 비정각 예약을 쓴다

**결정**: 실거래 캐너리는 `America/New_York` 10:17 평일 예약을 사용한다. 마이크로 GTAA의
기존 15:00 UTC 예약은 별도 경로이므로 바꾸지 않는다.

**근거**: 최근 `rebalance-live-canary` 예약 실행은 정각 혼잡 아래 42~80분, 두 차례는 약 9시간
지연됐다. GitHub 공식 문서도 매시 정각 예약의 지연·누락 가능성과 비정각 예약을 권고한다.
뉴욕 현지 시각을 쓰면 서머타임 전환에도 정규장 초반이라는 의미가 유지된다.

**기각한 대안**: 하루 여러 번 실주문 예약을 추가하면 지연 내성은 높아지지만, 미체결 주문과
중복 재조정의 위험 표면을 넓힌다. 첫 실제 체결 전에는 단일 비정각 예약이 더 작은 변경이다.

## 결정 10 - 운영 표의 성공 문자열이 아니라 섹션 JSON을 사실로 쓴다

**결정**: money-path는 생산 라이브 sidecar의 `첫 체결 전 최신 엣지 재검증` 제목 아래 펜스
안에서 첫 JSON 객체를 읽고, `allowed`와 `state`를 마지막 preflight 상태로 표시한다. 같은
문구가 있는 요약 표 행이나 작업 결과 `success`만으로 통과를 추론하지 않는다.

**근거**: 실제 생산 로그는 JSON 앞에 증거 나이와 원격 명령 종료 코드를 한 줄로 기록한다.
기존 파서는 펜스 전체가 순수 JSON이라고 가정했고, 표 행을 제목보다 먼저 찾아 드라이런
미리보기 블록까지 잘못 소비했다. 그 결과 성공한 `ENTRY_READY`를 증거 없음으로 표시했다.

**실패 폐쇄**: 제목 범위 안에 boolean `allowed`가 있는 JSON 객체가 없으면 이전과 같이
`preflight evidence absent`를 유지한다. 사람용 표의 `success`는 보조 정보로만 남긴다.

## 결정 11 - 레거시 캐너리 자본 설정을 현재 10% 계약의 이중 검사로 쓴다

**결정**: 라이브 설정의 `canary_capital_pct`를 단 1 운영 증거의 10%와 맞추고, 첫 주문
재검사가 두 값을 직접 대조한다. 센티넬과 최신 NAV가 실제 금액의 권위이며 이 설정은 같은
의도를 독립적으로 확인하는 선언이다.

**근거**: 스펙 001에서 도입한 5% 필드는 설정 검증만 되고 실제 주문 금액 계산에는 쓰이지
않았다. 스펙 176은 헌법 X.4에 따라 첫 자본을 정확히 NAV 10%로 다시 정의했지만 생산 설정에
옛 5%가 남아, 안전 한도처럼 보이는 값과 실제 계약이 달랐다. 값을 단순히 고치는 데 그치면
다시 어긋나도 발견하지 못하므로 첫 주문 관문에서 불일치를 실패 폐쇄한다.

**기각한 대안**: 5%를 실제 주문 상한으로 뒤늦게 적용하면 확정된 10% 명세·헌법과 충돌하고
현재 정수 주 구현성 계약도 달라진다. 필드를 삭제하면 과거 설정 호환성과 명시적 이중 검사를
잃는다.

## 결정 12 - 예약 시각과 실제 주문 시각을 분리해 검증한다

**결정**: `rebalance-once`의 실주문 모드는 서버의 실제 현재 시각을 XNYS 달력으로 검사하고,
정규장 밖이면 DB 마이그레이션이나 KIS 조회 전에 종료 코드 75로 실패 폐쇄한다. 종이매매와
주문 없는 미리보기에는 적용하지 않으며 우회 옵션을 만들지 않는다.

**근거**: 비정각 뉴욕 10:17 예약은 혼잡 가능성을 낮출 뿐 실제 시작 시각을 보장하지 않는다.
이력에는 약 9시간 지연도 있어 무장 뒤 같은 지연이 재발하면 장 마감 후 주문을 시도한다. 실제
돈을 움직이는 가장 안쪽 공통 진입점에서 재검사해야 GitHub 지연과 다른 호출 경로를 함께 막는다.

**기각한 대안**: 워크플로 이벤트 시각만 검사하면 러너 대기 시간을 놓치고, KIS의 장외 거부에
맡기면 불필요한 주문 시도와 오류 장부가 생긴다. 셸 게이트만 추가하면 다른 `rebalance-once`
라이브 호출이 보호되지 않는다.
