# 스펙 051 — FINDINGS (자율 파이프라인 생존 감시)

## 무엇을 만들었나

자율 시스템을 굴리는 스케줄 워크플로들의 사이드카가 *기대 주기보다 오래 멈췄는지*를
한 곳에서 보는 단일 감시자. 핵심 사이드카(자율 머니루프 직접 경로)가 정지하면 워크플로가
빨갛게 실패(loud)한다. 읽기 전용·돈 0 이동·Kernel 터치 0건.

## 왜 (빈칸의 실체)

- 각 워크플로는 자기 사이드카에 자기 `timestamp_utc` 만 찍는다 — **교차 생존 점검 없음.**
- `reports/health.py`(스펙 013)는 서버 안에서 라이브 DB 만 보고, 어떤 스케줄 워크플로로도
  발행되지 않는다. 컨테이너/운영자가 손쉽게 읽을 파이프라인-전체 생존 신호가 없었다.
- 침묵 정지의 위험: 전진 페이퍼가 멈추면 전진 엣지가 얼어붙는데, 자본 사다리는 계속
  `WAIT_EDGE` 만 보고 → "정상 누적"과 "죽어서 정지"가 구분 안 됨.

## 설계 결정

1. **순수 코어 + 얇은 워크플로.** 등급/종합 판정은 테스트된 `pipeline_liveness.py` 가
   하고, YAML 은 git show 로 사이드카를 모아 넘기기만 한다(스펙 050 게이트와 같은 철학).
2. **레지스트리 단일 출처.** 감시 대상 목록은 Python `default_specs()` 한 곳. 워크플로는
   `--manifest` 로 받아 iterate → YAML 에 브랜치 목록을 중복 정의하지 않는다.
3. **거짓 경보 최소화가 최우선.** 감시자가 늑대 소년이 되면 운영자가 무시한다. 그래서:
   - 평일(`* * 1-5`) 사이드카는 주말 갭(금밤→월밤 ≈72h)을 견디는 `max_age=80h`.
   - 매일 사이드카는 한 번 미스 정도는 안 울리는 `max_age=30h`(연속 정지만 잡음).
   - LATE(1~2주기)는 핵심이라도 DEGRADED(빨강 아님), STALE(2주기 초과)만 핵심→CRITICAL.
   - 연구/보고 트랙의 정지는 DEGRADED 까지만(빨강 아님).
4. **발행 후 실패(diagnostic survives).** 사이드카 발행 스텝은 `if: always()` 라 CRITICAL
   이어도 진단이 먼저 남고, 별도 마지막 스텝이 빨갛게 실패시킨다.
5. **돈 경로 무개입.** 정지를 탐지·보고만 하고 AUTOARM 을 끄지 않는다. 얼어붙은 엣지는
   이미 fail-safe(승격 불가)이므로 이 계층은 가시성 전용.

## 검증

- 단위 18건(파싱·OK/LATE/STALE/MISSING 분류·핵심/비핵심 종합·종료 코드·직렬화·레지스트리).
- 통합 4건(프로브가 사이드카 디렉터리를 읽어 판정·strict 종료 코드).
- **실데이터 엔드투엔드**: 워크플로 절차 그대로 origin 의 7개 사이드카를 git show 로 모아
  프로브 실행 → 전부 정확히 파싱, 종합 🟢 OK(현재 파이프라인 정상 가동 확인). 실제
  `LAST_RUN.md` 의 마크다운 표 timestamp 와 JSON timestamp 둘 다 파싱됨.
- 전체 스위트 통과(기준선 1856 + 신규 22 = 1878), 게이트 린트(src tests) 깨끗.

## 한계 / 후속 후보

- **감시자의 backstop**: 감시자 자신이 죽으면 빨간 실행이 안 뜬다. 사이드카
  `automation/pipeline-liveness-last-run` 신선도가 backstop(/sync·컨테이너 세션이 확인).
  더 강한 escalation(스테일 시 이슈 자동 생성·운영자 알림)은 외부효과라 별도 슬라이스.
- **주말/연휴 정밀화**: 지금은 넉넉한 고정 `max_age`. 거래일 달력 인지(연휴까지 반영)로
  더 타이트하게 좁힐 수 있으나, 거짓 경보 위험 대비 이득이 작아 보류.
