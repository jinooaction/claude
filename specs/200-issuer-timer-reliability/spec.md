# Feature Specification: 발행사 관측의 서버 정기 실행

**Feature Branch**: `codex/200-issuer-timer-reliability`
**Created**: 2026-10-02
**Status**: 코드/서버 가동 출시 완료, 실제96칸/24시간 관측·원본/사본 지문 대조 완료
**Input**: 기존 한국투자 단타 프로그램 완성. 공식 발행사 자료의 원격 정기 수집은 실제로 가동했으나 설정 15분에 비해 174~438분 간격이어서, 사용자 맥북이나 추가 가입에 의존하지 않는 관측 경로를 마련한다.

## User Scenarios & Testing

### User Story 1 - 서버가 제때 목록을 확인한다 (Priority: P1)

운영자는 맥북이 꺼져 있어도 지정된 공식 발행사 목록의 수신 결과와 수신 시각을 확인한다.

**Why this priority**: 현재 정기 실행은 13회 성공했지만 15분 설정의 실행 간격을 지키지 못했다.

**Independent Test**: 서버가 정상 가동되는 24시간 동안 매 15분마다 실제 시도 기록을 확인하고, 중단·실패 구간을 조회한다.

**Acceptance Scenarios**:

1. **Given** 서버와 지정 사이트가 정상, **When** 예정 시각이 도래, **Then** 20분 이내에 고정 목록 요청의 성공 또는 명시적 실패가 남는다.
2. **Given** 서버 중단·네트워크 장애, **When** 다음 예정 시각이 지나감, **Then** 누락 간격이 상태에서 드러나고 과거 관측으로 보충되지 않는다.

### User Story 2 - 같은 목록은 적게 받되 변경은 놓치지 않는다 (Priority: P1)

운영자는 같은 목록이 반복될 때 원문을 불필요하게 쌓지 않고, 목록이 바뀌면 제한된 본문을 수집한 사실을 확인한다.

**Why this priority**: 기존 18회에서 원문 55개·약 8.2MiB가 쌓였다. 그대로 15분마다 실행하면 현재 저장 한도에 빠르게 닿는다.

**Independent Test**: 같은 목록 96회, 새 항목, 직전 본문 실패, 하루 경과를 주입해 목록·본문 요청 수와 저장 바이트를 검사한다.

**Acceptance Scenarios**:

1. **Given** 검증된 목록과 본문이 24시간 안에 있고 직전 실패가 없음, **When** 목록 원문이 동일, **Then** 새 목록 관측은 남고 본문 재요청 생략 사유가 표시된다.
2. **Given** 목록 원문 변경·직전 실패·24시간 경과, **When** 다음 시도, **Then** 선택된 본문을 기존 요청 한도에서 다시 검증한다.
3. **Given** 한도가 가까움, **When** 다음 수집, **Then** 외부 요청 전에 중단하고 기존 자료를 삭제하지 않는다.

### User Story 3 - 손실과 사용 범위를 구분한다 (Priority: P2)

운영자는 서버 원본의 건강 상태와 복구 위치를 읽기 전용으로 확인하고, 서버 고장 때 마지막으로 보존된 시점을 안다.

**Why this priority**: 서버 한 곳만의 원본은 장기 관측 증거가 아니다.

**Independent Test**: 별도 원격 사본 두 번의 전체 파일 지문을 대조하고, 자료 없음·변조·복구 기준 불일치를 거부한다.

**Acceptance Scenarios**:

1. **Given** 완료된 서버 원본, **When** 원격 사본을 확인, **Then** 원본 지문·마지막 완료 시각·누락 구간이 일치한다.
2. **Given** 서버 자료가 유실, **When** 검증된 원격 사본으로 복구, **Then** 원래 관측을 보존하되 복구로 새로 알게 된 사실을 과거로 소급하지 않는다.

### Edge Cases

중복 타이머 시작, 장시간 실행, 서버 재부팅, 시계 역행, 같은 목록에서 본문만 수정,
이전 본문 일부 실패, 사이트 403/429/5xx, 잘린 RSS/본문, 부정확한 서버 시계,
원격 사본 게시 충돌, 복구 산출물 만료, 저장공간 한도, 원본 변조, 서버의 다른 계좌 비밀값 노출.

## Requirements

### Functional Requirements

- **FR-001**: 고정 발행사 목록은 사용자 맥북·GitHub 정기 이벤트와 독립된 서버 일정으로 확인한다. 각 예정 시각의 시작·성공·실패·누락을 읽기 전용으로 확인할 수 있어야 한다.
- **FR-002**: 실제 요청/수신/검증 완료 시각을 구분한다. 일정이 늦거나 재부팅된 동안의 사건을 이전에 관측한 것으로 보충하지 않는다.
- **FR-003**: 동일한 검증 목록이 24시간 안에 있고 선택 본문을 모두 검증했으며 직전 실행 실패가 없을 때만 본문 재요청을 생략한다. 생략 수는 자료 없음이나 검증 성공 수와 분리한다.
- **FR-004**: 목록이 바뀌거나 직전 실행이 실패하거나 본문 전체 검증 후 24시간이 지나면 기존 고정 한도 안에서 본문을 다시 확인한다. 본문만 바뀌는 경우를 발견하는 최대 지연은 정상 운용 시 24시간이다.
- **FR-005**: 목록·본문 원본과 시각 영수증, 실패, 실행 완료 기록은 추가 전용으로 보관한다. 기존 GitHub 수집 사슬과 서버 사슬은 서로 다른 출처로 식별하며 섞거나 소급하지 않는다.
- **FR-006**: 요청 속도·재시도·냉각·실행 시간·응답 크기 및 누적 저장 한도를 기존 수준보다 완화하지 않는다. 한도에 닿으면 외부 요청 전 실패를 기록하고 자동 삭제하지 않는다.
- **FR-007**: 서버의 계좌 설정·KIS 인증정보·주문 함수·자본·전략 승격에 접근하거나 영향을 주지 않는다. 별도 유료 서비스나 새 인증정보를 요구하지 않는다.
- **FR-008**: 종료된 서버 원본을 별도 위치에 지문 검증 가능한 형태로 보존하고, 마지막 성공·마지막 시도·복구 가능 기준을 읽기 전용으로 보고한다. 원격 보존 실패는 성공으로 표시하지 않는다.
- **FR-009**: 기존 GitHub 수집은 별도 자료 경로로 유지한다. 두 경로의 시각이나 원문을 합쳐 동일한 관측이라고 주장하지 않는다.

### Key Entities

- 예정 시도: 예정/시작/종료 시각과 실행 상태, 실제 요청 여부.
- 목록 관측: 고정 출처·원문 지문·수신 구간·선택 항목.
- 본문 관측: 선택 문서·원문 지문·수신 구간·검증 결과.
- 생략 사유: 동일 목록, 전체 검증 완료, 새로고침 기한 안 여부.
- 서버 완료 사슬: 실행 순서, 소스 지문, 누적 자료 지문.
- 원격 사본: 원본 완료 지문, 보존 시각, 복원 기준.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 정상 서버에서 연속 24시간 동안 예정된 96회 중 최소 92회가 예정 시각부터 20분 안에 성공 또는 명시적 실패로 기록된다. 남은 모든 시도는 누락으로 표시된다.
- **SC-002**: 변하지 않는 목록 96회와 첫 검증 완료 본문 3개를 재생할 때 목록 시도 96회가 보존되고 본문 요청은 첫 3개와 24시간 새로고침 시점의 최대 3개뿐이다.
- **SC-003**: 새 목록 항목·직전 실패·24시간 경과 각각의 경우 다음 정상 시도에서 선택 본문을 다시 확인한다. 실패를 사건 없음으로 바꾸지 않는다.
- **SC-004**: 실제 서버의 첫 수집과 후속 수집을 검증한 뒤, 별도 위치의 원본과 완료 지문이 같고 수정·삭제된 기존 자료가 0건이다.
- **SC-005**: 실주문·자본 변경·계좌 비밀값 출력 0건이며, 서버 원본과 기존 GitHub 원본의 소속을 혼동한 보고 0건이다.
- **SC-006**: 실제 고정 목록·본문 크기로 환산한 60일 정상 재생에서 기존 512MiB 한도에 닿지 않는다. 비정상적으로 많은 변경에는 기존의 요청 전 중단이 적용된다.

## Assumptions

이 기능은 위험 등급 3의 새로운 원격 연구 입력 경로다. 기존 서버와 무료 공식 자료를
사용하며 새 계정·비용·돈 경로는 만들지 않는다. 199의 Microsoft 출처와 제한을
초기 범위로 유지한다. 실제 발행 시각이나 전체 발표 범위는 증명하지 못하며 최초
관측 시각은 실제 확인 구간 뒤에만 놓는다. 기존 SEC403 기록은 보존한다.
서버 복구와 원격 보존은 자료의 손실 위험을 줄이기 위한 별도 단계이며, 최종 전략
검증이나 60세션 전진 관찰을 대신하지 않는다. 전체181 T013~T016은 그대로 남는다.
