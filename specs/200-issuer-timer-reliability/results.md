## 실제 파일 크기와 정상 60일 저장량 계산

검증된 최신 18run/72관측 원본의 파일 길이를 직접 읽었다. 목록 18관측은 동일
136,389바이트 원문 1개를 가리키며 최대 영수증은 432바이트였다. 본문 54관측은
서로 다른 54원문을 가리키고 평균 148,082바이트, 최대 169,401바이트이며 최대
영수증은 677바이트였다. 최대 완료 기록 파일은 1,235바이트다.

동일 목록을 15분마다 확인하는 정상 60일(5,760회)에 첫 본문 수집과 하루 단위
재검증을 보수적으로 183본문으로 잡고, 위 **관측 최대값**을 모든 파일에 적용하면
`5,760×(432+1,235)+183×(169,401+677)+136,389 = 40,862,583바이트`
(약 39.0MiB)다. 기존 누적 512MiB와 실행 전 64MiB 예약보다 낮다.
이는 실제 파일 크기를 이용한 상한 계산이지 5,760회의 서버 실행 증거가 아니다.
목록이 자주 바뀌거나 본문이 커지면 다시 계산해야 하며 한도에 닿으면 중단한다.

## 현재 코드 검증과 미확인 단계

서버 전용 CLI는 같은 목록의 검증 완료 본문만 24시간 이내에 재요청 생략하고
`selection.unchanged`를 기록한다. 기존 두 필드 완료 기록은 그대로 검증된다.
새 타이머는 별도 저장소와 고정 Microsoft 범위만 사용하며 KIS 환경 파일을
주입하지 않는다. 원격 내보내기는 고정 명령·고정 디렉터리·원본 지문 검사를 거치고,
복구 사본은 기존 GitHub 발행사 사슬과 다른 브랜치에 추가 전용으로 둔다.
로컬 모의 시험은 성공했으나 정확한 커밋의 원격 전체 검사·서버 배포·실제 첫 두 번의
서버 관측·원격 백업·연속 24시간의 96칸 확인은 아직 하지 않았다. 그러므로
SC-001/SC-004와 서버 정기 관측 완료를 주장하지 않는다.

전체 단타 프로그램 181 T013~T016의 통과 전략, 60세션 전진 관찰, 체결 동등성,
실제 주문·자본·정산 증거는 이 자료 수집 개선으로 대체되지 않는다.
